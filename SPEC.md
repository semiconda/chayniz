# Chayniz — v1 Specification

## Vision

Chayniz is a self-study drill app for someone learning Taiwanese Mandarin from zero. It targets:

- characters (recognition and recall),
- translation both directions (character/word → meaning, meaning → character/word),
- mastering pinyin, including the parts that trip up a non-native speaker (e.g. pinyin "yu" is always the ü sound,
  never "you"; "iu" is a contraction of "iou"; "ui" is a contraction of "uei"),
- short sessions — quizzes doable in spare 5-minute gaps, not long study blocks.

**Content pipeline.** Content is prepared *outside* the app: paste source material (teacher's slides, reference
book) into any LLM session with a prompt defining the CSV format below, get a CSV back, drop it into the app. The
CSV holds only raw facts per item — not question type or multiple-choice options. Those are generated by the app
at render time, so the same item can be asked different ways and distractors are drawn fresh each time.

## Scope

### v1 (this spec)

- Static single page (`app/index.html`), no backend, no build step, works on a phone, hostable on GitHub Pages.
- Lessons ship **with the site**: CSV decks live in `app/decks/`, are listed in `app/decks/manifest.json`, and are
  fetched and merged automatically when the page opens. Adding a lesson = commit a CSV + add its filename to the
  manifest; everyone opening the site gets the same content, with no upload step. Loading a CSV by hand remains
  available as an alternative (useful for trying a deck before committing it, and when opening the page from disk).
- Two modes, chosen by a switch on the start screen. **Test** (the default) is the drilling described throughout
  this spec. **Practice** shows the same selected words as a vocabulary table to read through — see
  "Practice mode" below. Both run off the same lesson selection; the mode switch is the only thing that decides
  which screen Start opens.
- Stateless multiple-choice drilling across eight question directions: six text directions (character ↔ meaning,
  character ↔ pinyin, pinyin ↔ meaning) and two listening directions (hear audio → pick the pinyin, hear audio →
  pick the character).
- No progress is saved anywhere. Every session starts fresh from the loaded CSV.
- Within a session, the app keeps a small amount of in-memory (non-persisted, reset on reload) runtime state: a
  shuffled row queue for coverage, and a distractor-repeat tracker (see "Question generation"). This is *not* a
  carve-out of the "no persistence" rule — it never survives a reload — it's runtime memory serving the same
  session, same reasoning the distractor tracker already relied on.

### Explicitly later (not v1)

Each of these is deferred because its real version needs infrastructure this app doesn't have yet — not because
the feature doesn't matter. v1 deliberately does not build a cheap stand-in for any of them:

- **Leitner spaced repetition (boxes, due dates, promote/demote on answer).** This needs durable, ideally
  synced progress storage. A version built on bare `localStorage` was considered and rejected mid-design: it
  doesn't survive iOS Safari's ~7-day eviction of an unvisited site's storage, it's wiped on private-browsing
  window close, and it's strictly per-device with no cross-device sync — all of which would silently corrupt or
  fork a learner's progress in exactly the "short sessions, on a phone, irregular use" pattern this app targets.
  Revisit once there's an actual plan for durable/synced storage (e.g. a backend, or at minimum explicit
  export/import).
- **Typed recall answers** (as opposed to multiple choice). In the original design this was gated behind Leitner
  box level; without a progression system there's no reason to introduce pinyin-answer normalization logic yet.
- **Speaking and reverse-audio questions** (see a word, pick which of several recordings matches; or record
  yourself). Listening questions themselves now exist — see "Audio" below — but anything requiring the learner to
  produce sound does not.
- **CSV tag-based filtering** (e.g. drill only "lesson 3"). `tags` is captured as metadata in the CSV now so content
  authors can start tagging, but no filter UI reads it yet.
- **In-app content generation** (OCR/parsing slides or PDFs, calling an LLM from inside the app). Content prep
  stays an external, manual step.
- **A real backend/database**, multi-device sync, multi-user accounts.
- **Multi-language / beyond Taiwanese Mandarin.**

## Data model

One CSV file, UTF-8, header row required. Traditional characters only (what the user will actually encounter in
Taiwan — slides, textbook, signage).

| column    | required | meaning                                                    |
|-----------|----------|-------------------------------------------------------------|
| `hanzi`   | yes      | the character or word, in Traditional script                |
| `pinyin`  | yes      | pinyin with tone marks, e.g. `yú`, `mā`, `xièxie`            |
| `meaning` | yes      | short English gloss                                          |
| `tags`    | no       | free-text metadata (e.g. lesson/topic); not read by v1 logic |

Example rows:

```csv
hanzi,pinyin,meaning,tags
謝謝,xièxie,thank you,greetings
魚,yú,fish,animals
```

**Decks and merging.** Every CSV listed in `app/decks/manifest.json` is fetched on page load and merged into one
pool, deduplicated on the exact `(hanzi, pinyin, meaning)` triple so a word repeated across lessons is drilled
once. A deck that fails to fetch is skipped rather than breaking the others.

**Lesson selection.** The start screen shows one chip per deck in the manifest, all on by default. Deselecting a
lesson removes its words from the pool entirely — including as *wrong options*, since distractors are sampled
from the same pool the questions come from. Selecting several lessons therefore mixes both the questions and the
options across all of them, which is the point: a word is only properly known when it can be told apart from
everything else learned so far. Selecting none is an error state, not an empty quiz. The chips are hidden when
the manifest holds a single deck (nothing to choose) and when a CSV is loaded by hand (they describe the bundled
lessons, not that file). This is lesson-level filtering only; the richer tag-filter UI remains deferred below.

Decks mirror the user's course text, 新版實用視聽華語 (Practical Audio-Visual Chinese) vol. 1, one file per lesson —
`app/decks/lesson01.csv` and so on. `app/decks/README.md` is the authoring guide and doubles as the worked example
of the format.

Notes for whoever writes the CSV-generation prompt:
- `pinyin` uses real tone marks (`nǐ hǎo`, not `ni3hao3`). v1 is multiple-choice only, so the learner never types
  pinyin — the column is read, not entered, and tone marks are what they'll actually encounter in textbooks and
  dictionaries. If typed recall is added later, the answer checker converts between tone marks and tone-numbered
  input for comparison; that's a problem for the checker to solve, not a reason to degrade what's displayed now.
- No `id` column in v1 — nothing in a stateless app needs a stable cross-session identity for a row. (Flag for
  review: this is a deliberate simplification; CSVs are regenerated per content batch rather than hand-maintained,
  so adding an `id` column back later costs nothing.)

## Audio

`app/audio/` holds one recording per distinct toned Mandarin syllable (1,223 files, ~45 MB), named by
tone-numbered pinyin — `ni3.mp3`, `lv4.mp3`. Because Mandarin's syllable inventory is closed, this set is
**bounded and complete**: any future lesson is covered without adding a single file.

**Source.** Taiwan's Ministry of Education 《國語辭典簡編本》 single-character audio package — human recordings of
the ROC MOE's own pronunciation standard, so the accent is genuinely Taiwanese rather than mainland. Licensed
CC BY-ND 3.0 TW, which permits redistribution with attribution. `app/audio/LICENSE.txt` carries the required
attribution and MOE's full usage notice; `tools/fetch_audio.py` reproduces the corpus from scratch.

**Why files are not trimmed.** Each MOE recording is a ~9-second reading: the syllable occupies roughly the first
half-second, then silence, then the dictionary definition read aloud. The licence forbids modifying entry content,
naming 音讀及釋義 (pronunciation *and* definitions) explicitly, while exempting adjustments that leave content
unchanged. So the files ship complete, re-encoded to MP3 but never cut, and the app simply **stops playback after
~0.62 s**. Playback behaviour is not redistribution. The trailing silence conveniently supplies the gap between
syllables of a multi-syllable word.

**Word audio is composed from syllables.** `謝謝` plays as its syllable files in sequence. An item qualifies for
audio questions only if *every* one of its syllables exists in the corpus; otherwise it simply never appears as a
listening question. The app never substitutes an approximate syllable.

## Choosing what to practise

A **mode** switch picks between Test and Practice. Test is the default, because drilling is what the app is for;
practice is the reference view you reach for when a word won't stick. Below it, the lesson chips choose the words
— both modes read the same selection — and a **Clear/All** control next to the chips selects or deselects every
lesson at once, since drilling a single lesson otherwise means deselecting all the others one at a time.

Four toggles on the start screen, all on by default, select which question types a session uses. Two are about
modality — **Reading**, **Hearing** — and two about script — **Pinyin**, **Characters**.

The script toggles are deliberately *not* symmetric:

- **Characters on** enables character↔english *and* character↔pinyin. Reading a character aloud is a character
  skill, so pinyin appears as the character's partner even when the Pinyin toggle is off.
- **Pinyin on** enables pinyin↔english only.
- Both on enables all three pairings.

Listening always runs **from** Chinese outward: the audio is always the prompt, never the answer. English is never
a prompt, because English isn't what's being learned. Which answers are offered follows the script toggles.

| Toggles | Question types |
|---|---|
| Reading · Pinyin · Characters | `hanzi↔meaning`, `hanzi↔pinyin`, `pinyin↔meaning` (6) |
| Reading · Characters | `hanzi↔meaning`, `hanzi↔pinyin` (4) — no `pinyin↔meaning` |
| Reading · Pinyin | `pinyin↔meaning` (2) |
| Hearing · Characters | `audio→meaning`, `audio→pinyin`, `audio→hanzi` (3) |
| Hearing · Pinyin | `audio→meaning`, `audio→pinyin` (2) |

At least one modality and at least one script must be selected; otherwise Start is disabled and the screen says
which is missing. The Hearing toggle is disabled outright when no audio corpus is reachable. The start screen
reports how many question types and how many words the current selection yields, since some items (those without
complete audio) drop out of listening-only selections.

In **practice** mode the Reading/Hearing pair is hidden rather than disabled: practice draws no such
distinction, since every row is readable and every row carries its own play button. Pinyin and Characters stay,
and there choose which *columns* the table shows.

Toggle state is not persisted — like everything else, it resets to all-on each time the page loads.

## Practice mode

The purpose is studying a lesson's vocabulary without going back to the book, and without the words being
scattered across its pages. Practice shows the selected lessons as one table:

| column | shown when |
|---|---|
| play button | always |
| character | **Characters** is on |
| pinyin | **Pinyin** is on |
| english | always |

Specifics that matter:

- **Rows keep textbook order**, not the shuffled order the quiz uses. A reference table you scroll twice should
  have a word in the same place both times.
- **Rows are grouped under a heading per lesson**, so several lessons can be open at once without losing track of
  which is which. Words are still deduplicated exactly as the quiz pool is, keeping the copy from the lesson that
  taught the word first.
- **Tapping anywhere on a row plays it**, not only the speaker button — a much bigger target for a thumb. Playback
  uses the same syllable-detection path as listening questions; nothing about the audio differs.
- **Words with no recording show a dimmed muted-speaker glyph** instead of a button. 16 syllables were never
  recorded (see "Audio"), so some words are reading-only; saying which is better than a button that does nothing.
- **A filter box** narrows the table by character, pinyin or english. Matching ignores tone marks, so typing
  `hao` finds `hǎo` — nobody types the marks. It is a plain substring match, which means a short query can match
  inside an English gloss (`nin` matches *mor**nin**g*); that is a filter behaving like a filter, not a defect.
- **Practice tracks nothing**, exactly like the quiz. It has no notion of which words you have read, and the
  filter text dies with the screen.
- **Both screens have a Back control** returning to the start screen. Before practice existed, the quiz had no
  way back at all except reloading the page.

## Question generation

Each question:

1. **Row selection:** rows are served from a session-scoped shuffled queue, not plain i.i.d. sampling. On load (or
   whenever the queue empties), shuffle all row indices and append them to the queue; draw from the front. This
   guarantees every row is seen once before any row repeats, and avoids the "same 2-3 items keep reappearing while
   others never show up" problem that pure uniform-random draws would cause in a short session on a small CSV.
   Like the distractor tracker below, this queue is in-memory only — reset on reload, never persisted.
2. Picks one direction uniformly at random from:
   - `hanzi → meaning` ("what does this mean?")
   - `meaning → hanzi` ("which character/word means this?")
   - `hanzi → pinyin` ("how do you read this?")
   - `pinyin → hanzi` ("which character/word is this pinyin?")
   - `pinyin → meaning` ("what does this pinyin mean?")
   - `meaning → pinyin` ("how do you say this in pinyin?")
   - `audio → pinyin` ("which pinyin do you hear?")
   - `audio → hanzi` ("which character do you hear?")
   — skipping the two audio directions for any item lacking complete syllable audio, and skipping any direction
   whose **answer column** (the column the options are drawn from — `meaning` for
   `hanzi → meaning`, `hanzi` for `meaning → hanzi`, etc.) doesn't meet the minimum distinct-value count below.
3. Builds 4 multiple-choice options: the correct value (from the picked row, in the answer column), plus 3
   distractors sampled uniformly at random from the *other* rows' values in that same column, excluding any value
   equal to the correct answer (so a duplicate value elsewhere in the dataset can't appear as a wrong option).
   **Homophones.** Mandarin has many (九 and 久 are both *jiǔ*; 他 and 她 are both *tā*), and telling them apart is
   part of learning the language, so both words stay in the deck. What must never happen is two of them sharing a
   question. Whenever the prompt identifies the word by sound alone — any audio direction, or either direction
   prompted by `pinyin` — distractors exclude every item whose pinyin equals the correct item's, because each of
   them would be an equally correct answer. Where the prompt is a character or an English gloss no such ambiguity
   exists, and a homophone makes an unusually good distractor. Note that when the *answer* column is `pinyin`
   this costs nothing extra: homophones share that value, so the "exclude the correct value" rule already covers
   them.

   **Same-length options.** Where the answer column is `hanzi` or `pinyin`, distractors are drawn from items with
   the same syllable count as the answer (measured as the character count of `hanzi`). A two-syllable answer sitting
   among one-syllable distractors is solvable on shape alone, without knowing any Chinese. When a deck holds fewer
   than three same-length alternatives the app fills the remainder from other lengths rather than refusing to ask —
   the giveaway is unavoidable at that point anyway — so decks should carry at least four words of each length they
   use. English glosses are exempt: their length doesn't track the Chinese word's.
4. Options are shown in random order.

**Distractor-repeat rule.** The app keeps an in-memory record (cleared on reload — not persisted), keyed by
(row index, direction), of the most recent distractor set shown. If a fresh sample would produce the exact
same 3-value set just shown for that (row, column) pair, resample again — up to a small fixed cap (e.g. 10
attempts) — before rendering. Keying includes the direction, not just the row index, so the same row asked two
different ways (its `meaning` options vs. its `pinyin` options, or heard vs. read) is tracked independently.

**Minimum dataset size.** The app requires at least **5** distinct values in the answer column before it can
generate a question in that direction. This is not 4: with exactly 4 distinct values, the distractor pool
(all values minus the correct one) has exactly 3 members, so there is exactly **one** possible 3-element
distractor set — "resample on repeat" would be a no-op, deterministically reproducing the same set every time,
which breaks the checkable test below at the boundary the rule itself would otherwise permit. At 5 distinct
values, the pool has 4 members and C(4,3) = 4 possible distractor sets, so resampling into a genuinely different
set is always possible. If the loaded CSV is too small for a given direction, that direction is skipped during
random selection.

## Checkable test

> Across N consecutive draws of the same (row, direction) pair in one session, the multiple-choice distractor set
> shown must never be identical to the immediately preceding distractor set shown for that same pair.

This is checkable two ways:
- **By inspection:** given the minimum-dataset-size rule above (≥5 distinct values in the answer column), the
  distractor pool always has ≥4 possible 3-element subsets, so "resample until different, capped at N attempts"
  is a direct, deterministic guarantee, not a probabilistic hope — verifiable by reading the implementation and
  confirming the minimum-size check gates every direction before it can fire.
- **Empirically:** load a small test CSV (comfortably above the minimum — e.g. 8-10 distinct values per column),
  force the same row/direction to be drawn repeatedly, and log the option sets shown; no two consecutive sets for
  that pair should be identical.

## Known limitations (intentional for v1)

- No progress survives a page reload, closing the tab, or revisiting later. This is a deliberate v1 boundary, not
  an oversight — see "Explicitly later" above.
- Nothing adapts to what the user already knows across sessions; the per-session row queue (above) guarantees
  even coverage *within* one session, but every new session starts over with no memory of past performance.
- Private/incognito browsing and multiple devices behave identically to normal use, since v1 stores nothing
  anywhere to begin with.
- **Distractors are drawn uniformly at random, not targeted at known pinyin confusions.** The vision names specific
  minimal-pair traps (e.g. "yu" vs. "you"-style spellings, `iu`/`iou`, `ui`/`uei`). Pure random sampling will only
  surface these as wrong options by chance, proportional to how many near-confusable pairs happen to exist in the
  loaded CSV — it does not deliberately drill the traps that motivated the app. Confusability-aware distractor
  selection (e.g. a small table of known trap pairs, preferred over random sampling when available) is a real
  feature with its own design surface and is deliberately deferred, on the same "don't bolt on a cheap version"
  reasoning used for typed recall — not solved by this spec.
- Homograph/polyphone rows (same `hanzi` value, different correct `pinyin` across rows) aren't specifically
  addressed. At v1 scale this is an accepted edge case, not a blocker.
- Bundled lessons require the page to be **served over http(s)** (GitHub Pages, or a local server). Browsers block
  `fetch` from `file://`, so opening `app/index.html` directly from disk shows a message and falls back to the
  manual CSV picker. This is a browser security rule, not something the app can work around without a build step.
- CSVs must be UTF-8 (a leading BOM is tolerated and stripped). Other encodings — e.g. Big5 from Excel on a
  Chinese Windows — would render as mojibake; encoding detection is deliberately not implemented.
- **Multi-syllable audio is concatenated citation forms, not connected speech.** `你好` plays as `nǐ` + `hǎo`,
  whereas a speaker would say *ní hǎo* (third-tone sandhi). Single characters — most of a beginner deck — are
  unaffected and sound exactly right; longer words sound like syllables read in isolation.
- **Syllables that only occur through sandhi or as contextual neutrals have no recording.** MOE records citation
  readings only, so `bú` (sandhi form of `bù`) and reduced neutrals like the second syllable of `xièxie` are
  absent. Items containing them are excluded from listening questions rather than approximated.
- **16 syllables are missing from the source corpus entirely**, because MOE shipped no recording for the only
  character that carries them — including common ones: `wo3` 我, `che1` 車, `guo4` 過, `nv3` 女, `men5` 們,
  `zi5` 子, `tou5` 頭, `zhe5` 著, `fen3` 粉, `man3` 滿, `nong4` 弄, `fo2` 佛, `lia3` 倆, `jiao2` 嚼, `diao3`,
  `ye5`. Any word containing one stays reading-only. These could in principle be recovered from MOE's
  word-level audio package (the opening syllable of a word beginning with that character), which is licensed
  identically but ships as a 15 GB five-part archive.
- Audio needs the page served over http(s), same as the bundled lessons.
